The governance gap — the single most consequential finding

The web layer is under governance: scripts/check_file_sizes.sh caps ~60 files with a both-directions ratchet, and it demonstrably works (a silent red-tree commit was caught by it on 08-09). The core, JS, and Rust layers are entirely outside it — and that is exactly where today's heavyweights live. commands/sound.ex (2,514 — the largest file in the repo), the whole cutup/ cluster, cli.ex, scene3d.ex, chrome.js, browser/mod.rs: no caps. The repo's own history says ungoverned decompositions get undone (TradingLive regrew 1,900 → 2,174; the xref cycle count regrew within a day).

Regrowth since the 08-08 measurement, five days ago: root-level core grew 67 files/17,859 lines → 75 files/20,464. chat_panel.ex grew 618 → 1,030 (capped, with reasons recorded). commands/ grew 5,481 → 9,459 — almost entirely one domain (sound, +3,125). The roadmap's thesis — "this is a rate, not a job" — is confirmed live.

2How verdicts were reached

Every large file gets one of four verdicts, using the house diagnostic from the archived modularization roadmap:

  • leave Feature-sized — one job written at length. The lines are the feature (a validated registry, one algorithm plus its corrections, a delegate wall that must be one module). Splitting it is churn.
  • cap Feature-sized but ungoverned — correct today, but nothing asserts it stays that way. Enters the size gate; seams pre-named for the day it grows.
  • split Overloaded — several jobs sharing a namespace. Split by the proven method: extract to a module, delegate or import so call sites stay byte-identical, zero behavior change, cap lowered in the same commit.
  • fix A defect found in passing, independent of size.

For web files, markup share is the diagnosis: 80% ~H is long (split by panel); 11% is overloaded (extract logic). Prior rulings were honored throughout — clusters already read and declared correct (browser_control/, scene3d/ pipeline, the commands facade, the post-split HELD files) were health-checked, not re-litigated.

5Agent core — the diagnosis confirmed, the state machine finally written down

agent/ 6,514 lines · chat.ex 1,510 (FROZEN) · attachments.ex 911 · stream_event.ex 622 · two server connections · six transport adapters

The argument for this part: the layering is genuinely clean and was verified so — Chat (one GenServer per conversation: ordering, queue, persistence, audit) never builds argv; ChatTransport (the three ways a turn leaves the BEAM: one-shot pipe, duplex pipe, server-backed) never touches the transcript; AgentBackend is a pure measured-facts table; AttachmentDelivery is the only I/O between them; StreamEvent is the single pure parser (five observed wire schemas → one struct, every mapping citing a probe). The three adapters do not share a shape, so the behaviour is a real abstraction, not ceremony.

agent/chat.ex 1,510 · FROZEN · "Phase 5"

hold — doc first, then split The standing ruling ("not obviously wrong; write the state machine down before any split") is confirmed and slightly understated: the review counted 10 read sites, 5 direct write sites, and 8 transition funnels on status — ~14 distinct transitions, against the ruled "eleven-plus." The real machine is status × transport-presence, because on a persistent transport :idle splits into two states (transport held vs not), with co-varying invariants (run/timer/turn_ref non-nil iff running; port/ handle set iff a transport is held; cost_baseline survives turns only while the transport does). The full transition table now exists — every state × event × guard × effect, from steer-receipt outcomes through the three exit shapes to the one transition that deliberately skips dispatch_next (:reset) — in the reviewer's report; the single most valuable next commit is landing it as documentation in or beside the file. Only then take the ruled seams: event projection (~280 nearly-pure lines) and queue/ledger choreography (~280), leaving the GenServer at ~900 as transitions + I/O.

Two live bugs found while verifying the machine

(1) :steered claimed without its receipt. The contract says :steered means "the backend proved acceptance" (chat.ex:162), and ClaudeDuplex advertises receipt: :boundary_replay — but its steer returns %{written_bytes:…} with no receipt key, so chat.ex:946 maps a successful Port.command straight to :steered. The purpose-built discriminator ChatMessageEncoder.operator_replay?/1 has zero production callers. The docs themselves call a false steered-claim "the single most damaging bug this feature can have." Consume the replay receipt, or downgrade the capability to :sent.

(2) Pipe-path model resolution uses the wrong namespace. Server transports correctly resolve ModelPolicy.model_for(agent, :chat) (chat.ex:776, with a comment explaining exactly why for_surface/1 is wrong) — but default_spawner injects ModelPolicy.for_surface(:chat) (chat.ex:1492). Concrete failure: global backend = codex + a confined conversation pinning :claude → claude is spawned with --model gpt-5.6-… from the codex bucket. The divergence the in-file comment warns about is live on the pipe path.

Also in chat.ex: the crash-recovered queue never self-dispatches and the next new submit jumps ahead of items the operator saw queued (:426–447 vs :472); the no-process capabilities/1 fallback hardcodes one-shot Claude, mislabeling the send button for duplex/codex conversations before the first message (:193); audit_run records state.agent while audit_delivery records effective_agent — cost attribution disagrees for confined conversations (:1279 vs :1011).
